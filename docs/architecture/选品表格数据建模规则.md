# 选品表格数据建模规则

> 日期：2026-10-08  
> 状态：第一版建模基线，待真实 Skill 选品表产出后补充字段字典与映射。  
> 适用范围：AI 初步选品、采购询价、利润复核、运营最终选品、竞品资料和 Listing 草稿。

## 1. 建模目标

数据库既要方便查询当前业务数据，也必须能够还原任意时期已提交的表格。当前尚未拿到 Skill 的最终表头，因此本版只固定不会随表头轻易变化的业务对象、版本关系和快照规则，不提前把临时字段写死为数据库列。

核心原则：

1. 四类业务表格是同一条选品链路在不同阶段的视图，不建立四份彼此脱节的商品副本。
2. 稳定、高频查询的字段使用 PostgreSQL 类型化列；Skill 的原始输出完整保存在不可变 `JSONB` 中。
3. 每次正式提交生成不可变版本；当前值通过“当前版本指针”读取，不能修改旧版本冒充历史。
4. 每个正式时期保存整表快照，使当时的表头、行顺序、字段值和引用版本可被准确还原。
5. 真实 Skill 表头确定后，采用“字段登记—映射—验证—迁移”的方式扩充模型，不删除原始输出。

## 2. 不采用的方式

- 不在初始选品表后无限追加询价、利润、复选和文案字段。这样会混淆岗位权限、版本归属和更新频率。
- 不为每个阶段复制一份完整商品数据。下游应引用上游的明确版本，只保存本阶段新增或修正的数据。
- 不把所有字段永久只存在 `JSONB`。需要排序、筛选、关联、约束或计算的稳定字段必须逐步提升为类型化列。
- 不根据中文表头直接生成永久列名。字段必须有稳定英文 `field_key`，中文名称只作为可版本化的显示标签。
- 不以空字符串或数字 `0` 代替缺失、失败、不可用、估算或未确认。

## 3. 总体结构

```text
selection_batch（一次 Skill 选品批次）
  ├─ selection_record（稳定的候选记录）
  │    ├─ selection_source_version（Skill 原始结果版本）
  │    ├─ quotation_round / supplier_quote_version（询价轮次与供应商报价版本）
  │    ├─ profit_review_version（利润计算与 AI 复核版本）
  │    ├─ final_selection_version（运营复选版本）
  │    ├─ competitor_set_version（3 条竞品资料版本）
  │    └─ listing_draft_version（标题与五点草稿版本）
  ├─ selection_stage_head（各阶段当前有效版本指针）
  ├─ selection_table_snapshot（某阶段一次正式整表快照）
  │    └─ selection_table_snapshot_row（快照行及其版本引用）
  └─ selection_flow_event（只追加的流转事件）

selection_output_schema（Skill 输出结构版本）
  └─ selection_output_field（表头字段定义与系统字段映射）
```

以上是逻辑名称。落地时可复用现有表名，但关系、版本语义和约束不得丢失。

## 4. 核心实体规则

### 4.1 选品批次 `selection_batch`

代表一次确定输入下的 Skill 执行及其表格产出。至少记录：

- `batch_id`、组织/店铺范围、平台及站点；
- Skill、提示词、模型、Sorftime 适配器及输出结构的明确版本；
- `task_id`、`run_id`、输入快照引用、生成状态和生成时间；
- 原始文件或外部证据的受控引用、校验和；
- 创建人、创建时间、失败类型和失败原因。

同一批次包含多条候选。重跑任务默认创建新批次或新运行记录，不覆盖旧批次。

### 4.2 候选根记录 `selection_record`

代表一条可持续流转的候选身份，只保存跨阶段稳定信息：

- `selection_id`；
- `batch_id`、`store_id`、平台/站点；
- 外部商品标识及可选的系统 `product_id`；
- 当前业务阶段、负责人、乐观锁 `revision`；
- 创建、更新时间和软归档状态。

`selection_id` 与商品主档 `product_id` 不混用。同一商品在不同店铺或不同来源批次出现时，保留不同候选记录；需要关联时显式建立来源关系。

### 4.3 Skill 输出版本 `selection_source_version`

每条候选的 AI 初选结果采用不可变版本保存：

- `source_version_id`、`selection_id`、递增 `version`；
- `schema_id`；
- `raw_payload JSONB`：完整、未经丢弃的 Skill 单行输出；
- `normalized_payload JSONB`：按当时映射规则规范化但尚未提升为列的字段；
- 已提升的类型化公共字段；
- 来源证据、输入快照、Skill/提示词/模型版本和 `task_id`、`run_id`；
- 草稿/已提交状态、提交人、提交时间及校验和。

原始输出只追加不改写。解析或映射规则修复时创建新规范化版本，或记录新的映射结果，不反向篡改历史原文。

### 4.4 询价模型

询价不能只是初选记录尾部的一个“采购价”字段，应至少拆为：

- `quotation_round`：一次询价轮次，引用初选版本，记录负责人、状态、开始/截止时间；
- `supplier_quote_version`：某供应商在该轮中的一版报价，保存供应商、规格、最小起订量、阶梯价格、币种、税费、运费、交期、有效期、数据确认状态及证据；
- 被选用于利润复核的报价版本引用。

这样可支持同一商品多供应商、多次改价、报价到期和历史比价。供应商敏感字段必须受后端字段级权限控制。

### 4.5 下游阶段版本

- `profit_review_version` 必须引用一个已提交的报价版本及计算规则版本，并分别保存程序计算结果、AI 建议、缺失项和确认状态。
- `final_selection_version` 必须引用一个利润复核版本，保存运营人工结论、理由和操作者，不允许 AI 自动写成最终批准。
- `competitor_set_version` 必须引用最终选择版本；一个集合包含 3 条有固定位置的竞品，每条保存标题、5 个要点、来源与采集时间。
- `listing_draft_version` 必须引用最终选择、竞品集合、真实规格、提示词和模型的明确版本，并保持待人工审核状态。

阶段记录只保存该阶段新产生的事实和结论，不重复复制全部上游字段。

### 4.6 当前版本指针 `selection_stage_head`

每条候选按阶段保存当前草稿、当前已提交和当前有效版本的引用。读取工作台当前数据时走指针；历史查询按版本 ID 读取。更新指针与创建版本、流转事件、审计记录必须处于同一事务。

新上游版本提交后，不删除下游记录，而是把受影响结果标记为“待复核”“已过期”或“已被取代”。

### 4.7 整表快照

正式提交一个批次或阶段表格时创建：

- `selection_table_snapshot`：批次、阶段、快照版本、输出结构版本、提交人/时间、行数、校验和、状态；
- `selection_table_snapshot_row`：快照 ID、稳定行号、`selection_id`、各阶段明确版本引用，以及用于精确重现的 `rendered_row JSONB`。

快照记录“当时看到的表”，阶段版本记录“每条业务数据如何演变”。二者都要保留，不能相互替代。筛选条件、排序和列展示配置如影响正式导出，也随快照保存。

### 4.8 流转事件 `selection_flow_event`

事件采用只追加方式，至少包括：候选/批次、源阶段、目标阶段、输入版本、输出版本、动作、操作者、原因、`trace_id`、发生时间。它用于审计和恢复，不取代业务版本本身。

### 4.9 导出任务 `selection_export_job`

每次 `.xlsx` 导出建立任务记录，至少保存：导出阶段、批次或快照 ID、结构版本、筛选与排序条件、申请人、申请时权限范围、状态、行数、文件引用、文件校验和、有效期、失败原因、`trace_id` 及创建/完成时间。

导出任务引用明确的整表快照或一组冻结的阶段版本，不能只保存“当前数据”这一可变化概念。文件本身不是新的业务事实来源；过期文件可以删除，但导出任务、审计和校验和继续保留。对象存储只保存生成文件，PostgreSQL 保存任务状态和可追溯关系。

## 5. Skill 表头与字段目录

`selection_output_schema` 记录某个 Skill 输出格式的版本、适用 Skill 版本、状态、生效时间和结构校验和；其子表 `selection_output_field` 每个表头一行，至少记录：

- 稳定 `field_key`、原始表头名、显示名和顺序；
- 原始类型、目标类型、格式、单位、币种语义；
- 是否允许为空及“缺失/零/估算/失败/不可用/已确认”的表达规则；
- 映射到的系统字段路径；
- 是否参与查询、排序、利润计算、身份匹配或权限脱敏；
- 映射规则版本和弃用状态。

真实 Skill 表头到位后，每个字段归入以下一类：

| 类型 | 存储方式 | 示例性质 |
|---|---|---|
| 身份与关联字段 | 类型化列 | 外部商品编号、站点、店铺范围 |
| 高频查询/筛选字段 | 类型化列并按查询建立索引 | 类目、排名、销量区间、状态 |
| 金额、比例、时间、数量 | 类型化列并保存单位/币种/确认状态 | 售价、重量、采集时间 |
| 来源与证据 | 受控引用及快照元数据 | 数据提供方、页面、采集运行 |
| 低频或尚不稳定字段 | `normalized_payload JSONB` | 新增实验指标 |
| 仅用于原样重现的字段 | `raw_payload` / `rendered_row` | 原始表头与展示文本 |

字段只有在满足以下任一条件时才从 `JSONB` 提升为正式列：跨多个 Skill 版本稳定；经常用于过滤、排序或关联；需要数据库约束；参与财务公式或关键决策。提升字段必须通过迁移回填，旧原始输出继续保留。

## 6. PostgreSQL 类型与约束

- 主键优先使用 UUID；版本号、行号使用正整数。
- 时间统一用 `timestamptz`，应用层以业务时区展示。
- 金额和比例使用明确精度的 `numeric`，不得使用浮点数；金额同时保存 ISO 4217 币种。
- 数量、重量、尺寸必须将数值与单位分开，禁止在一个字符串里混存。
- 动态对象使用 `jsonb NOT NULL DEFAULT '{}'::jsonb`；原始数组按结构使用 `[]` 默认值并做大小限制。
- 版本表至少有 `UNIQUE (selection_id, version)`；报价版本按报价主体建立等价唯一约束。
- 快照行至少有 `UNIQUE (snapshot_id, row_position)`，必要时另加候选唯一约束。
- 金额、数量和版本等字段建立合理 `CHECK`；业务缺失用 `NULL + value_status` 表达，不能自动写成零。
- 所有外键列按实际查询建立索引；PostgreSQL 不会自动为引用端外键创建索引。
- 已提交历史默认使用 `ON DELETE RESTRICT` 或软归档。只有真正附属于可丢弃草稿的子记录才可级联删除。
- 状态仍在快速演进时使用受约束文本及应用枚举；每次新增状态同步修改契约、数据库约束和测试。

## 7. 查询与索引基线

首批索引围绕真实访问路径设计：

- 工作台当前列表：`(store_id, current_stage, updated_at DESC)`；
- 批次候选：`(batch_id, selection_id)`；
- 阶段历史版本：`(selection_id, version DESC)`；
- 供应商报价：`(quotation_round_id, supplier_id, version DESC)`；
- 阶段快照：`(batch_id, stage, version DESC)`；
- 快照还原：`(snapshot_id, row_position)`；
- 待办或状态查询：根据实际过滤条件建立带范围的复合或部分索引。

不对所有 `JSONB` 盲目建立 GIN 索引。只有真实查询证明需要时，才为确定路径增加表达式索引或 GIN 索引。所有业务查询先带组织/店铺数据范围，再做字段过滤。

## 8. 真实 Skill 表头到位后的调整流程

1. 固定一份真实原始输出样本，同时记录 Skill、提示词、模型和数据源版本。
2. 建立表头字段字典，确认字段含义、数据类型、单位、空值语义、示例和来源。
3. 将字段分类为类型化核心字段、查询字段、动态扩展字段或仅展示字段。
4. 新建 `selection_output_schema` 版本和字段映射；旧结构版本继续可读。
5. 只为确认稳定的字段编写数据库迁移、约束和索引，从历史 `raw_payload` 回填。
6. 用样本核对行数、主键/候选匹配、类型转换失败、金额精度和快照校验和。
7. 新旧映射短期并行读取，通过集成测试后切换当前结构版本。
8. 更新本文、共享契约、OpenAPI、导入导出模板和前后端字段展示；不得只改页面表头。

表头删除、改名或拆分时只弃用映射，不删除历史字段和值。无法可靠转换的数据保留原值并标为转换失败，交给人工处理。

## 9. 并发、事务与权限

- 保存草稿使用 `expected_revision` 做乐观锁；提交使用幂等键，冲突返回 409。
- 创建正式版本、切换当前指针、生成整表快照、记录流转事件与审计必须原子提交。
- AI 任务开始时冻结输入版本，结束时再次校验当前指针；迟到结果只保存为历史，不能覆盖新结果。
- 后端按账号动作权限和店铺/组织范围授权。前端隐藏列不构成权限控制。
- 原始 Skill 输出、供应商信息和证据可能包含敏感数据；普通列表接口默认不返回完整 `raw_payload`，导出也必须使用同一字段权限。
- Listing 文案及其任务、竞品输入和历史版本为运营业务数据。采购默认角色无访问权限；管理员必须具有显式文案权限。权限调整不删除任何历史版本、任务或审计数据。

## 10. 验收标准

- 能按快照 ID 原样还原任意已提交时期的表头、行顺序和值。
- 当前工作台查询不需要扫描全部历史版本，也不依赖浏览器本地数据。
- Skill 新增或改名表头时，旧表格仍能按旧结构还原。
- 同一候选支持多个供应商、多次询价和明确的利润复核输入版本。
- 上游更新只使受影响的下游版本失效或待复核，不删除历史。
- 核心金额、时间、数量、状态可被数据库校验和高效查询，关键业务查询不依赖解析任意 JSON 文本。
- 重启、重新部署和数据库迁移后，当前指针、历史版本、快照和审计关系保持一致。
- 越权账号无法通过列表、详情、导出、对象 ID 或原始载荷接口读取其他范围数据。
- 任一阶段可按当前冻结快照或指定历史快照导出 `.xlsx`；相同快照和结构版本重复生成时，业务数据内容一致且导出行为可审计。

## 11. 与当前实现的衔接

现有 `selection_records`、询价版本、利润复核版本、最终选择版本、竞品版本、AI 任务和 Listing 草稿版本可继续复用。后续实现前应核对并补齐：

1. 选品批次、Skill 输出结构/字段目录和不可变原始输出版本；
2. 各阶段当前版本指针；
3. 询价轮次、多个供应商及报价选择关系；
4. 阶段整表快照与快照行；
5. 只追加流转事件及提交时的原子事务；
6. 历史表的删除约束、外键索引和字段级访问控制。

本文只确定建模规则，不代表上述表和迁移已经完成。真实 Skill 选品表产生后，先按第 8 节完成字段审查，再调整物理表结构。

### 11.1 AI 选品表导出首版落地（2026-10-09）

迁移 `20261009_0006` 已为 `initial_selection` 落地最小不可变导出能力：

- `selection_table_snapshots` 保存阶段、结构版本、筛选条件、冻结店铺范围、行数和内容校验和；
- `selection_table_snapshot_rows` 按稳定行号保存候选 ID、候选修订号及当时的 `rendered_row`；
- `selection_export_jobs` 保存任务状态、申请人授权修订、快照引用、私有文件引用、文件校验和、失败原因和有效期；
- 应用仓储不提供修改快照行的接口，重新导出或重新查询创建新任务/快照，不覆盖旧快照；
- 当前结构版本为 `initial_selection.v1`，只包含现有 `selection_records` 已确认字段。真实 Skill 表头尚未登记，不将临时字段编造成正式列。

当前生成在请求内完成，但任务状态和阶段导出器接口保留了后续 Worker 执行边界；未来异步执行必须重新加载账号授权并检查冻结店铺范围。

### 11.2 采购询价表导出落地（2026-10-09）

迁移 `20261009_0007` 增加独立 `quotation.export` 权限和询价版本 `submission_status`。既有询价版本迁移为 `submitted`，当前询价写接口也明确写入 `submitted`；尚未提供草稿保存或草稿导出接口。

`quotation` 快照按候选查询最新的已提交询价版本，在同一数据库查询与事务中冻结：候选 ID、候选修订号、选品来源版本、询价版本、供应商、报价、币种、MOQ、单件运费、交期、数据状态、登记人和登记时间。后续提交新询价版本不修改旧快照行。

当前物理模型仍是每条候选的单供应商追加版本，不具备询价轮次、多供应商并列报价、询价规格和报价有效期。导出器不构造这些字段。利润复核和最终选品导出器仍未注册。
