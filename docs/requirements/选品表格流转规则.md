# 选品表格流转规则

> 日期：2026-10-08。依据：当前方向文档和 ADR-003。
>
> 本文规定系统内四类表格的交接规则，作为后续前后端开发和验收依据。文档建立不等于功能已实现；现有接口的差距见第 10 节。利润公式、筛选门槛及未明确的操作权限仍需单独确认。
>
> 数据库实体、版本、整表快照和 Skill 表头适配规则见 `docs/architecture/选品表格数据建模规则.md`。

## 1. 流转主线

```text
AI 初步选品结果提交
  -> 选品表：采购待询价
  -> 采购询价草稿 -> 人工提交
  -> 采购询价表：待利润复核
  -> 程序计算 + AI 复核完成
  -> 利润选品表：运营待复选
  -> 运营人工选择/淘汰并提交
  -> 最终选品表
       ├─ 选择通过：采购待处理（不等于采购已审批）
       └─ 选择通过 + 3 条竞品资料完整：待生成标题和五点
```

流转以单条商品候选记录为单位。一个批次中某条记录缺资料或失败，不应阻塞其他满足条件的记录。淘汰项保留历史，在正常下游待办中不再出现。

## 2. 数据关联与版本

- 统一使用已有 `selection_id` 关联选品、询价、利润复核、最终选择、竞品资料和 Listing 草稿。`product_id` 表示商品主档时，与候选编号分别保存，不混用。
- 四张表是同一业务链路的阶段视图，不能靠复制 Excel、再次上传或手工录入编号完成交接。
- 根记录保留 `store_id`、平台/站点、来源、负责人、阶段、`revision`、创建及更新时间。
- 每个已提交成果都是不可变版本，保存操作者、提交时间、输入版本及必要的任务/运行引用。
- 询价可有多个历史版本；每次利润复核必须明确引用一个已提交询价版本；最终选择引用一个当前有效的利润复核版本。
- 竞品资料独立保存修订版本并关联最终选择版本；文案引用最终选择、竞品、真实规格、提示词及模型配置的明确版本。
- 多次发现相同商品时可以关联同一商品主档，但不同店铺或来源批次的候选不能自动合并。重新使用资料须显式引用并保留来源。
- 已流转记录的店铺不得静默更换；需要跨店复用时建立新候选/经营范围，保留来源关系并重新授权、复核。

## 3. 保存、提交和有效性

每个阶段分别表达三个维度，不能只用一个 `stage` 字段兼任：

| 维度 | 含义 | 状态 |
|---|---|---|
| 业务阶段 | 记录走到哪里 | 初步选品、询价、利润复核、最终选择 |
| 交接状态 | 是否已交给下一岗位 | 草稿、已提交、已退回 |
| 成果有效性 | 能否作为当前输入 | 当前有效、待复核、已过期、已被新版本取代 |

- **保存草稿**：允许不完整数据，只对有读取权限的责任岗位展示；不创建下游待办，不触发 AI，不改变当前已提交版本。
- **提交**：后端验证权限、范围、必填项、输入版本和当前状态，成功后冻结版本并创建下游待办。
- **接收/领取**：记录责任人和时间，不复制上游数据；领取不自动增加对象或店铺权限。
- **退回**：由被授权的下游责任人填写原因和缺失项，回到上游修订；保留提交、退回和旧版本记录。
- **重新提交**：创建新版本，并重新计算哪些下游成果需要复核；旧待办更新或失效，不重复创建。
- **撤回/淘汰**：必须有操作权限和原因；已发生实际采购等外部动作时只能进入变更/异常处理，不能假装历史动作从未发生。

接口必须区分“保存”和“提交”。若继续使用同一写入路径，必须有明确的命令语义和测试，不能默认每次保存就是提交。

## 4. 各阶段交接条件

| 阶段 | 谁负责 | 交接条件 | 下游获得 |
|---|---|---|---|
| 选品表 | 采购工具台中获授权的选品任务使用者；AI 执行 | 生成成功、输出结构通过校验、来源/版本可追溯、商品与店铺范围明确；不存在阻断的商品身份或规格疑点 | 采购待询价记录 |
| 采购询价表 | 获授权采购人员 | 引用已提交候选，供应商/报价时间/有效性及币种明确；缺失成本项标注；满足已配置的利润复核输入要求 | 固定询价快照、待利润复核任务 |
| 利润选品表 | 程序与 AI；发布结果由后端校验 | 引用当前已提交询价版本；计算配置和 AI 版本可追溯；任务成功；满足已确认筛选规则；无阻断缺失项 | 运营可复选的候选及依据 |
| 最终选品表 | 获授权运营人员 | 引用当前有效利润复核；人工选择/淘汰明确；淘汰、退回需理由；目标店铺在授权范围 | 选择通过项进入采购待处理；淘汰项进入历史 |
| 标题与五点草稿 | 运营专属；管理员需显式权限 | 当前最终选择为通过；3 条竞品各有标题和 5 条非空要点；真实规格可用；规定提示词版本已配置 | 关联输入版本的文案草稿，待人工审核 |

补充规则：

- “估算”不等于“已确认”。是否允许某个估算字段参与筛选由版本化规则决定；缺失值不能当作零。
- 未配置利润公式或门槛时，显示“规则待配置”，不能擅自定义百分比或生成“通过”结果。
- AI 拒绝、不确定、缺数据、工具失败分别记录；未通过项在采购复核/历史视图可查，不自动进入运营正常复选列表。
- 不完整的竞品资料可保存草稿，但不能提交为文案生成输入。竞品参考中的卖点不自动成为本商品事实。
- **运营通过选品后即可交给采购待处理；竞品资料不完整只阻止文案生成，不自动阻止采购查看最终选择。** 实际采购仍需独立满足规格、数量、供应条件及审批要求。
- 最终选择不是采购批准，AI 文案草稿也不是发布批准；本规则不新增采购下单或平台发布权限。

## 5. 上游变化和下游失效

只有新的草稿被提交，或已提交输入被确认失效/撤回，才改变当前下游有效性。编辑草稿不应让正在使用的已提交成果突然消失。

| 变化 | 处理规则 |
|---|---|
| 提交新报价、运费、售价、币种、规格等复核输入 | 旧利润复核标记待复核；旧最终选择和相关文案标记需重新验证；禁止继续用于新的采购或生成任务 |
| 报价到期、费用依据失效 | 标记对应利润复核及依赖成果过期，生成补资料/复核待办 |
| 新利润复核提交 | 运营重新确认选择；不把 AI 建议自动转换成人工最终选择 |
| 运营撤回或改为淘汰 | 撤销未完成采购待办及文案生成资格；已有采购/外部动作进入人工异常处理 |
| 仅竞品标题/五点提交新版本 | 旧文案标记待重新生成/审核；不自动使报价和利润结论失效 |
| 文案任务引用的规格或提示词正式版本更新 | 保留旧文案与输入绑定；新任务使用明确版本，不静默重写历史；当前是否需重新审核由影响规则决定 |
| 仅内部备注等不影响业务输入的字段修改 | 记录修订和审计，不无条件使全部成果失效 |

AI 任务开始时冻结输入。任务结束时再次校验输入是否仍是当前有效版本；旧任务结果只能保存为历史/过期成果，不能覆盖当前指针。遇到无法判定影响的关键修改，标记待人工核对，不继续自动流转。

## 6. 工作台与访问权限

- 采购工具台展示第 1、2、3 步；运营工作台展示第 4、6 步。
- 采购人员可读取已提交最终选品用于采购交接；第 5 步页面位置仍待确认，读取需求不等于新增下单页面。
- 采购修改询价；运营修改最终选择和竞品资料；AI 结果以独立版本保存，不能直接改写人工登记原值。
- 运营读取利润结论、依据和必要产品资料；供应商敏感信息或无关采购资料不因表格流转自动开放。
- 管理员可按授权监管全链路，管理账号/板块的权限不自动赋予询价、最终选择或业务审批写权限；“全业务只读”权限不能用于写入。
- Listing 文案仅在运营工作台提供。普通采购账号不得读取或操作；管理员读取和操作也必须使用明确动作权限。
- 后端同时检查账号、板块、动作权限及数据范围；运营按授权店铺过滤，采购按已授权组织/团队/店铺范围读取。
- 跨岗位交接不改变店铺范围。接收人无权访问时显示“待分配责任人/权限”，交由有权管理员处理，不能自动越权授权。
- 列表、详情、搜索、导出、文件、缓存和 AI 调用均使用相同范围；通过修改对象 ID 或店铺参数不得读取其他店铺。

## 7. 待办、事务与可靠性

- 一次提交在同一数据库事务内完成：保存成果版本、更新当前指针/阶段、记录流转事件、写入审计及 Outbox（需要异步派发时）。任一项失败全部回滚。
- 阶段交接事件记录记录编号、源/目标阶段、输入/输出版本、操作者、责任岗位、时间、原因及 `trace_id`。
- 异步消费者据事件创建待办/AI 任务；事件可重复投递，但不得产生重复任务。
- 命令携带 `expected_revision` 和幂等键。版本冲突返回 409，前端刷新后由用户确认；相同幂等键但不同请求内容必须拒绝。
- 待办至少关联记录、阶段和输入版本；记录责任人、状态及阻断原因。没有责任人时进入该岗位授权范围内的待领取池。
- PostgreSQL 为正式状态来源，页面刷新或服务重启不得丢失提交记录。Redis/队列只负责传递和调度。
- AI/MCP 未配置或执行失败时保留原记录和失败原因，允许有权限人员对同一快照重试；不能伪造完成或自动进入下一步。
- 跨节点恢复按任务/动作编号核对状态。未来采购或平台外部写入状态未知时先回查，不盲目重复执行。

## 8. 界面与接口最低要求

每行至少展示：记录编号、商品、店铺、阶段、交接状态、有效性、版本、负责人、最后更新时间、缺失项/阻断原因、允许的下一步。

详情支持查看上游来源和历史版本；无权字段不返回给客户端。“暂未产出”“已失效”“任务失败”和“无权访问”必须区分，不都显示空表。

后台必须提供查询、保存草稿、提交、退回及版本历史能力。流转动作、状态枚举、条件失败码在 `shared/contracts/` 与 OpenAPI 中统一，前端不得自行推断状态或绕过后端校验。

每个阶段的表格必须支持导出 `.xlsx`，至少覆盖选品表、采购询价表、利润选品表和最终选品表。导出必须由后端生成并遵循以下规则：

- 导出请求明确指定阶段以及批次、当前查询快照或历史快照；同一文件中的行必须来自一致的数据版本，不能在分页下载过程中混入新提交数据。
- 后端重新执行账号动作权限、店铺/组织范围和字段脱敏检查；页面可见或拥有单条读取权限不自动等于拥有批量导出权限。
- 缺失、零、估算、失败、不可用和已确认在 Excel 中保持可辨认；金额、时间、数量使用正确单元格类型，币种和单位不能丢失。
- 文件附带导出说明，至少记录阶段、快照/版本、导出时间、数据范围、筛选条件、行数和结构版本；不得把密钥、内部提示词或无权字段写入文件。
- 每次导出记录操作者、权限范围、参数、快照、行数、结果状态、文件校验和及 `trace_id`。失败导出也保留失败原因。
- 导出文件设置有效期并受控下载；采购账号不得借助导出获得 Listing 文案或其他未授权数据。

2026-10-09 实施说明：当前实现 AI 选品表 `initial_selection` 和采购询价表 `quotation` 导出，分别使用 `selection.export`、`quotation.export` 及 PostgreSQL 冻结快照。询价导出只包含最新已提交版本；运营不得导出供应商和报价数据，管理员也必须显式获得询价导出权限。利润表和最终选品表导出仍待后续逐阶段接入，不得调用当前接口伪装成功。

## 9. 验收场景

| 场景 | 必须证明的结果 |
|---|---|
| 正常交接 | 同一记录从选品进入询价、复核、运营复选和最终选品，跨账号可读取授权范围内的已提交成果 |
| 草稿保存 | 不完整询价/竞品可以保存，下游无新增待办或 AI 调用 |
| 输入不足 | 显示缺失项，不能生成已通过的利润结果 |
| 淘汰与退回 | 理由、操作者和版本可查，不在下一阶段正常待办中出现 |
| 报价更新 | 提交新版本后旧利润和依赖最终选择标记待复核；旧历史仍可按权限查看 |
| 竞品更新 | 只使依赖文案需要重新验证，不无理由回退报价和利润 |
| 并发和重复点击 | 旧 revision 返回 409；重复提交不生成两条同版本待办/任务 |
| 旧 AI 结果晚到 | 不覆盖新输入的当前成果 |
| 岗位与跨店访问 | 运营不能改询价、采购不能改运营选择、只读管理员不能写业务；越权列表/详情/导出被后端拦截 |
| 权限撤销 | 交接不增加权限，旧会话和异步执行不能继续使用已撤销授权 |
| 重启与事务故障 | 提交成果和待办可恢复；失败事务不留下半流转记录 |
| 文案岗位隔离 | 运营按动作权限和店铺范围访问；采购返回 403；管理员无明确权限也返回 403 |

完整验收需要一条实际跨岗位业务数据；真实 AI 未接入前可用明确的测试适配器验证，但不能宣称真实 DeepSeek/Sorftime 链路已通过。

## 10. 与现有实现的衔接及待细化项

已检查 `docs/requirements/六步选品流程字段状态与接口.md` 和 `backend/api/app/modules/selection/`。现有实现具备 `selection_id` 关联、询价/利润/最终选择版本、3 条竞品校验、乐观锁及 AI 任务查询边界。

后续实施应逐项补齐，并更新对应契约：

1. 保存草稿与提交分离，补充交接状态、下游待办、退回和历史查询。
2. 将询价修改直接回退阶段的行为调整为“草稿不影响当前成果，提交新版本才触发失效”。
3. 竞品支持不完整草稿及独立版本，提交/生成时严格校验 3 条 × 5 要点。
4. 明确展示失效原因与历史引用，不仅把旧结果从当前响应中隐藏。
5. 业务写接口使用专用动作权限，不以管理员全业务只读权限放行写操作。
6. 补齐原子审计/流转事件、幂等、异步输入快照及结果过期校验。

尚未确认的项目参数：利润公式及费用口径、筛选门槛、允许估算的字段、报价有效期规则、第 5 步页面位置、第 6 步发起/修改/审核人。实现时明确显示待配置或待确认，不自行编造业务门槛。
