# AI商品运营中台系统构建方向

> 本文档用于后续所有对话快速读取项目方向。PDF 仅作为资料来源；本文不是逐字复述，而是把建设思路压缩成可执行、可修改的系统纲领。

## 当前阶段重构方向（2026-10-08，已确认）

用户通过《构建方向.txt》确认了新的阶段业务路线。本节是当前实施优先级，后续章节保留长期方向和治理原则；若旧的首版重点、开发顺序或验收范围与本节冲突，以本节为准。本次仅同步项目指引，不表示代码已完成改造。

### 六步业务主线

```text
DeepSeek + 用户 Skill + Sorftime MCP
-> 选品表
-> 采购人工询价与登记
-> 采购询价表
-> DeepSeek 利润复核
-> 利润选品表
-> 运营人工复选并补充 3 条竞品标题和五点
-> 最终选品表
-> 采购人员开展采购

最终选品表中的竞品资料 + 规定提示词 + 真实商品规格
-> DeepSeek 生成本商品标题与五点草稿
```

1. 接入 DeepSeek 作为 AI 大脑，使用用户编写的 Skill，接入 Sorftime MCP 完成初步选品，得到选品表格。
2. 选品表展示在系统内，采购人员据此询价，人工登记采购询价表。
3. DeepSeek 复核询价表、分析利润空间，形成筛选后的利润选品表。程序执行可验证的金额公式，AI 负责复核、解释和筛选建议；数据不足时不得伪造盈利结论。
4. 运营查看利润选品表，人工再做一次选品，形成最终选品表。运营为最终选品补充 3 条竞品的标题及各自五点，用于后续 Listing 编写。
5. 采购人员查看最终选品表，开展采购工作；实际采购仍由责任人决定并遵守审批边界。
6. DeepSeek 使用规定提示词和最终选品表中的竞品标题、五点，生成本商品的标题与五点；结果作为待人工审核草稿，不得将竞品事实直接视为本商品事实。

### 工作台与接口

| 工作台 | 当前明确展示的步骤 |
|---|---|
| 采购工具台 | 第 1、2、3 步 |
| 运营工作台 | 第 4、6 步 |

第 5 步的执行人为采购人员，但页面归属仍需后续确认。2026-10-09 最新决定将第 6 步调整为运营工作台专属：普通采购账号不得读取、生成、编辑、审核或查询 Listing 文案历史；管理员也必须拥有明确的文案监管或业务权限，不能仅凭管理员身份访问。

预留 DeepSeek Provider、用户 Skill 执行、Sorftime MCP 和后续其他应用的适配接口。AI/MCP 接口不代替业务授权，不直接从前端持有凭证。

### 保留的工程与治理边界

- 核心后端沿用已确认的 FastAPI，复用已有 PostgreSQL、认证、账号授权、审计和接口契约。
- 员工使用自己的账号登录，管理员分配可见板块、动作权限和店铺范围；运营数据按授权店铺隔离。
- 表格是业务成果的系统视图，正式数据与历史版本持久化，保留记录关联、输入快照和任务/运行编号。
- 利润结论区分缺失、零、估算、失败、不可用和确认值，保留报价、费用、汇率、币种与来源时间。
- AI 不自主批准或执行采购等高风险动作。历史执行不得被最新表格或提示词覆盖。
- 图片/视频、自动上架、仓库履约、广告及补货继续作为长期方向，当前阶段优先完成上述六步链路，不要求同步建设所有模块。

来源与确认记录见 `docs/decisions/ADR-003-当前阶段六步选品采购与文案流程.md`。

四类表格的岗位交接、提交条件、版本失效、权限、待办与验收规则见 `docs/requirements/选品表格流转规则.md`。流程开发必须读取该规则；未确认的利润门槛和操作权限不自行假定。

## 1. 总体定位

建设目标不是重新做一堆独立 AI 工具，而是把已经存在的选品 Skill、Listing 撰写、自动上架、图片制作、广告中台等能力，统一纳入一个围绕商品全生命周期运转的通用业务中台。

系统的核心价值是：统一商品对象、统一任务流、统一权限审批、统一版本记录、统一外部接口、统一效果验证，让 AI 能力可复用、可追踪、可灰度、可回滚、可持续迭代。

一句话方向：

> 以商品和经营项目为中心，以任务为执行载体，以审批和版本为控制线，以数据和评测为改进闭环，构建一个可长期迭代的 AI 商品运营中台。

## 2. 建设边界

系统应该整合和治理现有能力，而不是一开始推翻重做。

首版重点：

- 接入已有五类能力：选品、Listing、自动上架、图片/视频、广告运营。
- 打通商品从发现到运营的主流程：发现产品 -> 询价测算 -> 运营认领 -> 产品迭代 -> 正式采购 -> 内容交付 -> 上架发布 -> 仓库履约 -> 广告运营 -> 补货/退出。
- 建立业务底座：商品、规格版本、经营项目、店铺商品、报价、采购履约、内容包、任务运行、评测发布。
- 建立治理底座：用户、组织、店铺授权、权限、审批、日志、版本、发布、回滚。
- 建立迭代底座：反馈案例、候选版本、测试、灰度发布、质量监测、效果复盘。

暂不作为首版重点：

- 不把财务记账、税务申报、工资核算做进系统。
- 不让 AI 自主决定采购、广告预算、绩效结论等高风险事项。
- 不强行把所有现有工具都改造成 Agent 或 MCP。
- 不用“本地保存”替代真正的数据权限、审计和备份。

## 3. 系统主线

系统围绕两条闭环建设。

业务闭环：

发现产品 -> 询价与测算 -> 运营认领与迭代 -> 正式采购 -> 图片/文案/Listing -> 自动上架 -> 仓库履约 -> 广告和经营 -> 补货或退出。

能力改进闭环：

任务结果 -> 员工纠错 -> 审核案例 -> 候选版本 -> 离线测试 -> 小范围验证 -> 批准发布 -> 持续监测 -> 必要时回滚。

这两条闭环必须通过商品、任务和版本编号关联，避免业务结果散落在聊天记录、表格、个人电脑或工具目录里。

## 4. 核心模块

### 4.1 岗位工作台

按岗位组织任务，而不是按模型名称组织首页。

主要岗位包括：产品开发、采购、运营、美工、仓库、主管、IT。每个岗位看到自己相关的待办、审批、异常、资料和运行结果。

### 4.2 商品与经营项目

商品不是 Listing，Listing 也不是 SKU。系统需要分清：

- 商品主档：公司内部商品概念。
- 规格/变体/版本：颜色、尺寸、材质、包装、数量等可变形态。
- 经营项目：某商品/变体在某店铺、站点、负责人下的运营计划。
- 店铺商品：面向平台的 listing、ASIN、seller_sku 等。

统一编号解决“是谁”，版本解决“当时是什么”，来源解决“为什么可信”。

### 4.3 选品 Skill 接入

保留现有 6 个选品 Skill 的业务逻辑和专属字段，不强迫它们共享同一套评分权重。统一输入输出即可：

- 输入：站点、机会类型、关键词/ASIN、规则、样本、数据快照、任务编号。
- 输出：候选、依据、风险、缺失资料、推荐状态、后续动作。

接入原则是先保留历史样本和正式版本，再做接口适配；不能只把提示词复制给另一个模型就宣称完成迁移。

### 4.4 询价与可售性测算

系统保留产品立项测算，不扩展为公司财务核算。

测算输入包括供应商报价、规格、包装、物流、平台费用、目标售价、广告假设、汇率、税费处理口径等。程序执行公式，AI 只解释假设、风险和缺失资料。

缺尺寸、报价过期、关键费用未确认时，不得自动通过。

### 4.5 运营认领、迭代与采购

候选商品通过测算后进入认领。运营选择店铺、站点、负责人并建立经营项目。

认领不是覆盖商品资料。不同店铺可以共享基础规格，但文案、素材语言、价格、广告和销售计划分别管理。

采购必须基于已审批的规格版本、数量、供应条件和授权额度执行。AI 可以给建议，但不能替责任人补签。

### 4.6 内容、图片、视频与 Listing

复用已有内容生产能力，但统一交付包。

正式上架使用的不是“文件夹里最新的图片”，而是审批通过的内容包：商品版本 + Listing 版本 + 素材版本 + 目标店铺 + 审批记录。

系统可做自动检查：文件尺寸、缺图、语言、必填字段、套装数量、颜色/形状/文案风险等。AI 检查只辅助标注疑点，最终一致性由对应责任人复核。

### 4.7 自动上架与外部执行

自动上架保留已有程序，重点改造授权、资料契约、重复执行防护和平台状态回查。

建议状态：

- 草稿
- 待审核
- 可提交
- 已提交/平台处理中
- 已处理但需检查
- 失败
- 待人工核对
- 需补资料

任何外部动作都要有 action_id、run_id、目标对象、审批版本、执行节点、平台回执和失败原因。断网、超时、重复请求、平台异步处理都必须进入可追踪状态，不能只停在终端日志。

### 4.8 采购、仓库与补货

系统记录采购明细、供应商、数量、商品版本、计划交期、ERP 编号、到货质检、包装标签、发运入仓和异常。

补货建议使用“保护期需求 + 安全库存 - 库存位置”的框架，结合销售基线、季节窗口、MOQ、箱规、预算和运营审批。AI 不直接下单。

ERP 承担正式采购、库存和发运事实。中台维护映射、计划、待办和分析，避免建立两套互相冲突的库存实账。

### 4.9 广告与运营

已有广告能力继续使用，中台补齐商品关联、策略审批、操作记录和观察结果。

广告建议单应包含店铺、对象、当前状态、拟修改值、理由、证据快照、风险级别、影响范围、审批人和有效期。高风险动作如预算变化、批量修改、商品发布等必须人工审批。

系统不能把销量变化全部归因于 AI；必须记录库存、促销、价格、评论、账号健康等干扰因素。

## 5. 数据与接口方向

### 5.1 核心数据对象

首版至少需要以下对象：

- product_id：商品主档。
- variant_id + spec_version：规格版本。
- project_id：经营项目。
- listing_id / seller_sku / ASIN：店铺商品。
- opportunity_id / quote_id：机会与报价。
- po_id / po_line_id / shipment_line_id：采购与履约。
- asset_id / content_version / package_id：内容与发布包。
- task_id / run_id / action_id：任务与执行。
- case_id / eval_run_id / release_id：案例、评测与发布。

所有可变记录都要带版本号或修订号。历史执行引用快照，不被最新内容覆盖。

### 5.2 数据标准

金额需记录币种、含税口径、汇率来源和日期。尺寸重量统一存标准单位并保留原值。时间统一存储并显示店铺/用户时区。指标需包含观察期、归因口径、来源更新时间和采集时间。

空值、未开放、零值、失败、估算值不得混用。

### 5.3 权威来源

不同数据要明确权威来源：

- 商品规格与审批：商品主档模块。
- 采购、库存、发运事实：ERP 或真实承担业务的系统。
- 广告实际配置/结果：广告系统与平台回执。
- Listing 状态：平台处理结果与回查。
- 市场估算与竞争数据：外部数据源，如 Sorftime。
- 跨部门任务和审批：中台。

中台可以汇总和同步，但不能用 AI 建议覆盖真实业务事实。

### 5.4 接口契约

任务接口至少包含：

```text
task_id
project_id / product_id / store_id / marketplace
capability_id / release_id / spec_version
input_refs
requested_by / permission_scope / environment
mode: draft | dry_run | execute
trace_id / deadline / budget_limit
result: status / output_refs / evidence_refs / warnings / error_code / run_id / action_id / external_receipt_id
```

接口必须区分业务不通过、缺数据、模型结构错误、工具失败和外部执行未知，不能全部用 success=false 表达。

## 6. 用户、权限与治理

系统必须做真权限，而不是前端隐藏按钮。

基础制度：

- 一人一账号，员工身份与服务身份分开。
- 最小权限：按角色、组织、店铺、业务动作、敏感字段控制。
- 入职、调岗、离职都要有权限授予、回收和交接。
- 正式区与试验区分离，试验区不能越权写真实店铺。
- 高风险动作独立审批，审批记录绑定对象、版本、摘要、审批人、时间、有效期和条件。
- 管理员操作留痕，关键日志追加写、独立备份或校验。

AI 可以辅助解释、摘要、比对和建议，但不能跳过责任人、审批人和授权范围。

## 7. AI 持续迭代机制

AI 能力要分正式区和试验区。

迭代流程：

1. 发现问题：真实任务错误、人工修改、工具失败、业务观察。
2. 审核案例：判断是资料错误、需求变化、规则问题、模型问题还是程序问题。
3. 提出改进：形成新规则、提示词、程序、模型配置或数据样本。
4. 隔离验证：固定数据和基线，在试验区运行，禁止真实写入。
5. 批准试用：限制岗位、店铺和任务范围候选发布。
6. 正式升级：达到条件后进入正式路由，记录 release_id。
7. 持续观察：监控错误、成本、质量和业务影响，必要时回滚。

只有菜单中保留“进化中心”不算完成；至少要跑通一轮真实反馈 -> 审核案例 -> 候选改进 -> 新旧对比 -> 批准试用 -> 正式/回退演练。

## 8. 技术落地建议

首版采用“模块化应用 + 独立执行节点”的方式，先保证边界清晰。

建议顺序：

1. 盘点并冻结现有五类工具：负责人、运行环境、输入输出、账号授权、依赖、失败样本、是否可后台运行、备份方式。
2. 建立公共底座：用户/店铺权限、商品与经营项目、任务、素材、日志、版本。
3. 接入选品结果和内容交付，完成第一个跨岗位试点。
4. 打通询价 -> 测算 -> 认领 -> 内容包 -> 自动上架的小范围闭环。
5. 接入 ERP 可用数据、采购/仓库/补货任务和主管看板。
6. 建立试验区、案例库、评测脚本和发布/回滚流程。

优先做可验证的接口和任务契约，不急于把所有内部调用改成 MCP。MCP/API 是连接层，不是权限、审计和业务授权的替代品。

## 9. 首版验收标准

首版验收不看按钮数量、页面美观或模型数量，而看可证明的行为。

必须能证明：

- 现有能力被统一纳入商品、项目、任务和版本体系。
- 跨店接口、搜索、文件、缓存、导出被正确限制。
- 采购、图片、文案、上架引用审批过的规格和内容版本。
- 外部执行断线不重复写入，状态未知可核对，旧新入口不双写。
- 数据质量能区分空值、估算、实际、时间、币种和来源。
- 节点宕机、服务重启、备份恢复后无任务丢失或重复执行。
- 至少完成一轮 AI 能力迭代演练。
- 有责任人、待办、堵点、培训和运维手册。

阻断项：

- 越权或错店写入。
- 不可控重复动作。
- 密钥泄露。
- 关键产品事实错配。
- 无法恢复的任务或资产丢失。
- 规则和审批门槛未签署。

## 10. 长期方向

长期目标是形成一个持续进化的商品运营生产系统：

- 商品资产长期沉淀，不随人员和电脑变化丢失。
- AI 能力通过案例库、评测、灰度、发布和回滚稳定升级。
- 主管通过真实任务进度、质量证据、成本和风险看板管理，而不是看 AI 使用次数。
- 员工可以反馈和纠错，反馈进入待审核案例，不自动变成公司真理。
- 外部系统各司其职：ERP 管交易事实，广告系统管广告事实，平台管上架事实，中台管业务协同、任务治理和 AI 迭代。
